feat: manage the PostgREST role settings `pgrst.db_schemas`, `pgrst.db_extra_search_path`, and `pgrst.db_max_rows` in declarative schemas under the Supabase profile (#476). A file can now declare `ALTER ROLE "authenticator" SET "pgrst.db_schemas" = '…'` (or `RESET` it) on the API roles `authenticator`, `anon`, `authenticated`, and `service_role` in the default database scope. Previously database scope refused the statement as cluster DDL, and cluster scope silently ignored it. Other `pgrst.*` keys (such as `pgrst.jwt_secret`) stay platform state. These settings are now their own `roleSetting` facts, so plans emit `ALTER ROLE … SET` / `RESET`. `schema export` writes them to the cluster `role_settings.sql` and records that file in the export manifest (`roleSettingsFiles`). A new policy field, `managedRoleSettings`, selects these settings (setting names match case-insensitively), and the Supabase policy sets it. A plan manages them only against an isolated shadow (`isolatedShadow` / `--isolated-shadow`), and only when a file declares one with `ALTER ROLE` or the export manifest records them: a directory exported before this change does not plan a `RESET` of the target's settings, and a warning names them. pg-delta resets the managed settings on the shadow so a deleted line plans a `RESET`. When a file carries `ALTER ROLE`, pg-delta compares the attributes and settings of the shadow's existing roles in the catalog before and after the load, and refuses any change other than a managed setting, naming it. With any other shadow (co-located, or a separate server without `isolatedShadow`), these settings are left unmanaged: the export's role-settings file is skipped with a warning, a hand-written `ALTER ROLE` is refused as cluster DDL with a hint to use an isolated shadow, and the plan neither sets nor resets them. `--skip-cluster-ddl` skips `ALTER ROLE` outside the export's role-settings file. `prove` requires a clone from a different PostgreSQL lineage for any plan that changes these settings, as it does for a cluster-scope plan. `CREATE ROLE`, `DROP ROLE`, membership `GRANT`/`REVOKE`, and `COMMENT`/`SECURITY LABEL ON ROLE` are still refused as cluster DDL in database scope.
