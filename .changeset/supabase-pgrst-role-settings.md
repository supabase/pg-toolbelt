feat: manage PostgREST `pgrst.*` role settings in declarative schemas under the Supabase profile (#476). A file can now declare `ALTER ROLE "authenticator" SET "pgrst.db_schemas" = '…'` (or `RESET` it) on the API roles `authenticator`, `anon`, `authenticated`, and `service_role` in the default database scope. Previously database scope refused the statement as cluster DDL, and cluster scope silently ignored it. These settings are now their own `roleSetting` facts, so plans emit `ALTER ROLE … SET` / `RESET`, and `schema export` writes them to the cluster `roles.sql`. A new policy field, `managedRoleSettings`, selects these settings, and the Supabase policy sets it. Database scope accepts these `ALTER ROLE` statements only with an isolated shadow (`isolatedShadow` / `--isolated-shadow`): pg-delta resets the managed settings on the shadow so a deleted line plans a `RESET`, loads the files, then compares the shadow's roles, role settings, and memberships in the catalog before and after the load, and refuses any change other than a managed setting, naming it. With any other shadow (co-located, or a separate server without `isolatedShadow`), these settings are left unmanaged: an `ALTER ROLE` is refused as cluster DDL with a hint to use an isolated shadow, the plan neither sets nor resets them, and a warning names the target's settings. `prove` requires a clone from a different PostgreSQL lineage for any plan that changes these settings, as it does for a cluster-scope plan. `CREATE ROLE`, `DROP ROLE`, membership `GRANT`/`REVOKE`, and `COMMENT`/`SECURITY LABEL ON ROLE` are still refused as cluster DDL in database scope.
